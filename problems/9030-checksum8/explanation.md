# 9030. 8 位补码校验和（Intel HEX） —— 小白详细题解

> 串口、Bootloader、Modbus ASCII、NMEA……几乎所有简单的通信协议都带一个"校验和"字节，用来发现传输中翻转的比特。这道题的算法只有一个循环，关键是理解 **无符号数回绕** 和 **补码**。

---

## 📖 第一步：先读懂题目

用大白话说就是：

> 把所有字节加起来，只看最后 8 位（对 256 取余），然后找一个数 `C`，让"总和 + C"刚好凑成 256 的倍数。

拿示例 1（`:0300300002337A1E`）走一遍：

| 字节 | 十进制 | 累加和 | 累加和 mod 256 |
|---|---|---|---|
| 0x03 | 3 | 3 | 3 |
| 0x00 | 0 | 3 | 3 |
| 0x30 | 48 | 51 | 51 |
| 0x00 | 0 | 51 | 51 |
| 0x02 | 2 | 53 | 53 |
| 0x33 | 51 | 104 | 104 |
| 0x7A | 122 | 226 | 226 |

`226 + C ≡ 0 (mod 256)` → `C = 256 - 226 = 30 = 0x1E`，和 HEX 记录最后的 `1E` 一致。

**几个需要注意的细节：**

1. 和可能远超 255（10000 个 255 相加是 2550000），只关心它的**低 8 位**。
2. 当低 8 位已经是 0 时（示例 2），校验和是 `0` 而不是 `256`——`256` 根本装不进一个字节。
3. `len` 可以是 0：空数据的和是 0，校验和也是 0。

---

## 🧰 第二步：需要的 C 语言知识

### 1. 无符号整数的回绕

C 标准规定：**无符号整数溢出时自动对 2^N 取模**，这是完全合法、可移植的行为。

```c
uint8_t x = 250;
x = (uint8_t)(x + 10);     // 260 mod 256 = 4，x 变成 4
```

所以用 `uint8_t` 累加，天然就是"只保留低 8 位"。（有符号数溢出则是未定义行为，千万别依赖。）

### 2. 补码：取反加一

在 8 位里，`-x` 的二进制表示就是 `~x + 1`（每一位取反，再加 1）：

| x | 二进制 | ~x | ~x + 1 | 十进制 |
|---|---|---|---|---|
| 226 | 1110 0010 | 0001 1101 | 0001 1110 | 30 |
| 0 | 0000 0000 | 1111 1111 | 1 0000 0000 → 截成 0000 0000 | 0 |

而 `x + (~x + 1) = 1111 1111 + 1 = 1 0000 0000`，低 8 位恰好是 0——这正是校验和要满足的条件！

### 3. `~` 作用在 `uint8_t` 上的陷阱

`~sum` 之前，`sum` 会先被提升成 `int`：`~(uint8_t)226` 是 `0xFFFFFF1D`（一个负的 `int`），不是 `0x1D`。所以结果必须**再转回 `uint8_t`**：`(uint8_t)(~sum + 1u)`。

## 💡 第三步：思路一 —— 用 32 位累加，最后取低 8 位

### 思路

1. 用 `uint32_t` 把所有字节加起来（10000 × 255 远小于 2^32，不会溢出）
2. 取低 8 位：`low = sum & 0xFF`
3. 校验和 = `(256 - low) & 0xFF`（最后的 `& 0xFF` 把 256 变回 0）

### 手动模拟（示例 3）

| 步骤 | 值 |
|---|---|
| sum = 200 + 100 + 50 | 350 |
| low = 350 & 0xFF | 94 |
| 256 - 94 | 162 |
| & 0xFF | **162** |

示例 2：`sum = 256`，`low = 0`，`256 - 0 = 256`，`256 & 0xFF = 0` ✅

### 代码

```c
uint8_t checksum8(const uint8_t* buf, size_t len) {
    uint32_t sum = 0;                         // 用 32 位累加，不用担心中途溢出

    for (size_t i = 0; i < len; i++) {
        sum += buf[i];
    }

    uint32_t low = sum & 0xFFu;               // 只保留低 8 位，等价于 sum % 256
    return (uint8_t)((256u - low) & 0xFFu);   // low 为 0 时 256 & 0xFF = 0
}
```

### 复杂度分析

- **时间复杂度 O(n)**：每个字节加一次。
- **空间复杂度 O(1)**。

---

## 🚀 第四步：思路二 —— 让 `uint8_t` 自动回绕，再取反加一

### 思路

既然只关心低 8 位，那就**直接用 `uint8_t` 累加**：每次加法都自动对 256 取模，循环结束时 `sum` 就是"和的低 8 位"。然后用补码"取反加一"得到校验和，连 `256 - x` 的特殊情况都不用单独考虑。

在 8 位 MCU（8051、AVR）上，这比 32 位累加快得多：每个字节只要一条 8 位加法指令。

### 手动模拟（示例 2）

| 步骤 | sum（uint8_t） |
|---|---|
| 初始 | 0 |
| + 255 | 255 |
| + 1 | 256 → 回绕为 **0** |
| ~0 + 1 = 0x100 → 截成 uint8_t | **0** |

### 代码

```c
uint8_t checksum8(const uint8_t* buf, size_t len) {
    uint8_t sum = 0;

    for (size_t i = 0; i < len; i++) {
        sum = (uint8_t)(sum + buf[i]);        // 自动对 256 取模
    }

    return (uint8_t)(~sum + 1u);              // 取反加一 = 8 位补码 = (256 - sum) mod 256
}
```

> 💬 `(uint8_t)(0u - sum)` 也是同样的意思：无符号的"0 减去 sum"会回绕成 `2^32 - sum`，低 8 位正好是补码。

## 🔌 嵌入式实战

**Bootloader 校验一行 Intel HEX 记录**：把**包括校验和在内**的所有字节加起来，结果为 0 就是正确的。

```c
/* rec 是已经从 ASCII 十六进制转成字节的一整行（含末尾校验和） */
bool hex_record_ok(const uint8_t* rec, size_t len) {
    uint8_t sum = 0;
    for (size_t i = 0; i < len; i++) sum = (uint8_t)(sum + rec[i]);
    return sum == 0;      /* ❌ 示意代码：不是本题要提交的函数 */
}
```

**发送端打包一帧：**

```c
uint8_t frame[8] = {0x55, 0xAA, 0x03, 0x10, 0x20, 0x30};
frame[6] = checksum8(frame, 6);    /* ❌ 示意：最后一个字节填校验和 */
HAL_UART_Transmit(&huart1, frame, 7, 100);
```

**它能发现什么、不能发现什么？**

- 能发现：任意**单个字节**出错、单个比特翻转。
- 不能发现：两个字节**交换顺序**（加法交换律）、一个字节 +1 同时另一个 -1。
- 对可靠性要求更高的场合（Modbus RTU、CAN、存储校验）会换成 **CRC**。

## ⚠️ 第五步：小白常见错误

1. **返回 `256 - sum % 256` 而不处理 0**：和的低 8 位为 0 时得到 256，转成 `uint8_t` 虽然碰巧是 0，但如果函数返回类型是 `int`（很多人这样写），就直接错了。
2. **`~sum + 1` 不转回 `uint8_t`**：`sum` 被提升成 `int`，`~226 + 1` 是 `-226`，赋给 `int` 变量后打印出来就是负数。
3. **忘了取反加一，直接返回和**：`return sum;` 得到的是"累加和"而不是"补码校验和"，Intel HEX 用的是后者。
4. **用 `int8_t` / `char` 累加**：`char` 在很多平台上是有符号的，`buf` 里的 `0xFF` 会被当成 `-1`，而且有符号溢出是未定义行为。
5. **用 `int` 循环变量和 `size_t len` 比较**：`for (int i = 0; i < len; i++)` 会触发有符号/无符号比较警告，`len` 很大时还会出错，循环变量用 `size_t`。
6. **用 `^`（异或）代替加法**：异或校验（XOR checksum，NMEA 用的就是它）是另一种算法，`[200,100,50]` 异或得到的是 `130`，不是 `162`。

## 📊 第六步：方法对比

| 方法 | 时间复杂度 | 空间复杂度 | 特点 |
|---|---|---|---|
| 32 位累加 + `(256 - low) & 0xFF` | O(n) | O(1) | 直观，容易理解 |
| `uint8_t` 回绕 + 取反加一 | O(n) | O(1) | 最简洁，8 位 MCU 上最快 |
| 暴力枚举 0~255 找 C | O(n + 256) | O(1) | 能做对，但没有理解补码 |
