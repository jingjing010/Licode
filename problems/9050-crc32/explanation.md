# 9050. CRC-32 校验 —— 小白详细题解

> CRC-32 是"出镜率"最高的校验算法：以太网、ZIP、PNG、各种 Bootloader 都在用。它和 9049 的 CRC-16/MODBUS 是同一个套路（反射算法），只多了"结果取反"这一步。本题重点学习**查表法**，因为固件动辄几百 KB，逐位法太慢。

---

## 📖 第一步：先读懂题目

和 CRC-16/MODBUS 对比：

| | CRC-16/MODBUS | CRC-32（本题） |
|---|---|---|
| 宽度 | 16 位 | 32 位 |
| 反射多项式 | 0xA001 | **0xEDB88320** |
| 初值 | 0xFFFF | **0xFFFFFFFF** |
| 结果异或 | 0 | **0xFFFFFFFF**（即取反） |

示例 3：空数据时 crc 一直是 0xFFFFFFFF，最后异或 0xFFFFFFFF 得到 **0**。

示例 2：`"a"` 只有一个字节 0x61，按逐位法算 8 次后再取反，得 0xE8B7BE43。

**容易忽略的细节：**

1. **最后的取反不能忘**，否则 `"123456789"` 会得到 0x340BC6D9。
2. 返回值是 `uint32_t`，最大约 42.9 亿，超出了 `int` 的范围。自己打印时要用 `%u`（或转成 `long long` 用 `%lld`），不能用 `%d`，否则会显示成负数。
3. 常量最好写成 `0xEDB88320u`（带 u 后缀），明确是无符号数。

---

## 🧰 第二步：这道题需要的 C 语言知识

### 1. 为什么要初值全 1、结果取反？

- 如果初值是 0，数据开头多几个 `0x00` 字节，CRC 不会变化——"前导零"检测不出来。初值全 1 解决了这个问题。
- 结果取反则让"数据末尾追加 0"这种错误也能被检测出来。

### 2. `static` 全局变量和"只初始化一次"

```c
static uint32_t table[256];       // static：只在本文件可见，不会和别人的名字冲突
static bool ready = false;

if (!ready) { build(); }          // 第一次调用时建表，以后直接用
```

在 MCU 上更常见的是把表写成 `static const uint32_t table[256] = {...};`，编译时就确定，放在 Flash 中，不占 RAM、也不用初始化。

### 3. 无符号 32 位运算会自动"模 2³²"

`uint32_t` 运算溢出时自动丢弃高位（这是 C 标准保证的），所以 CRC 计算中不需要额外 `& 0xFFFFFFFF`。

## 💡 第三步：思路一 —— 逐位计算

### 代码

```c
uint32_t crc32(const uint8_t* buf, size_t len) {
    uint32_t crc = 0xFFFFFFFFu;                      // 初值全 1
    for (size_t i = 0; i < len; i++) {
        crc ^= buf[i];                               // 新字节异或进低 8 位
        for (int k = 0; k < 8; k++) {
            if (crc & 1u) {                          // 最低位为 1
                crc = (crc >> 1) ^ 0xEDB88320u;      // 右移并异或反射多项式
            } else {
                crc >>= 1;
            }
        }
    }
    return crc ^ 0xFFFFFFFFu;                        // 结果取反
}
```

### 复杂度分析

- **时间 O(8n)**：本题 n = 2×10⁵，约 160 万次循环，电脑上很快；但在 72MHz 的 MCU 上校验一个 512KB 的固件就要几百毫秒。
- **空间 O(1)**。

---

## 🚀 第四步：思路二 —— 查表法（工业标准写法）

### 为什么能优化？

每个字节的 8 次循环，结果只取决于 `(crc ^ byte)` 的低 8 位——只有 256 种可能。提前算好：

```
table[v] = 把 v 当作 crc 做 8 次逐位运算的结果
```

于是每个字节只需要一次查表、一次移位、一次异或：

```
crc = (crc >> 8) ^ table[(crc ^ byte) & 0xFF];
```

### 手动验证一项

`table[1]`：c = 1，第 1 次最低位为 1 → `0 ^ 0xEDB88320 = 0xEDB88320`；之后 7 次依次右移/异或……最终得到 `0x77073096`。这正是网上各种 CRC32 表的第二项，可以用来检查自己的建表代码。

### 代码

```c
static uint32_t crc32_table[256];
static bool crc32_ready = false;

static void crc32_init(void) {
    for (uint32_t v = 0; v < 256; v++) {
        uint32_t c = v;
        for (int k = 0; k < 8; k++) {                   // 逐位法算出 8 步后的结果
            c = (c & 1u) ? (c >> 1) ^ 0xEDB88320u : (c >> 1);
        }
        crc32_table[v] = c;
    }
    crc32_ready = true;
}

uint32_t crc32(const uint8_t* buf, size_t len) {
    if (!crc32_ready) crc32_init();                     // 第一次用时建表
    uint32_t crc = 0xFFFFFFFFu;
    for (size_t i = 0; i < len; i++) {
        crc = (crc >> 8) ^ crc32_table[(crc ^ buf[i]) & 0xFFu];   // 每字节一次查表
    }
    return crc ^ 0xFFFFFFFFu;
}
```

### 🔌 嵌入式实战：分块计算 + Bootloader 校验

固件通常是一块一块收到的（每包 128~1024 字节），不可能等全部收完再算。把"初值"和"取反"拆出来，就能**增量计算**：

```c
uint32_t crc32_update(uint32_t crc, const uint8_t* p, size_t n) {
    for (size_t i = 0; i < n; i++)
        crc = (crc >> 8) ^ crc32_table[(crc ^ p[i]) & 0xFFu];
    return crc;
}

// 使用：crc = 0xFFFFFFFF; 每收到一包 crc = crc32_update(crc, pkt, len); 全部收完 crc ^= 0xFFFFFFFF;
```

注意：STM32 的硬件 CRC 外设默认**不反射、不取反、按 32 位字输入**，算出来和本题的标准 CRC-32 不一样，要配置 REV_IN / REV_OUT 并手动取反才能对上——这是实际项目中的经典"坑"。

### 复杂度分析

- **时间 O(n)**，**空间 1KB**（256 × 4 字节）。

---

## ⚠️ 第五步：小白常见错误

1. **忘了最后取反** → 得到 0x340BC6D9，和标准值对不上。
2. **用 `int` 存 crc** → 有符号数右移可能补 1，且溢出是未定义行为。
3. **`printf("%d", crc)` 打印** → 大于 2³¹ 的值显示成负数。
4. **查表下标没有 `& 0xFF`** → `crc ^ buf[i]` 是 32 位的，下标越界。
5. **多项式用了 0x04C11DB7 却右移** → 不反射的多项式要配左移，反射的 0xEDB88320 才配右移。
6. **分块计算时每块都重新从 0xFFFFFFFF 开始、每块都取反** → 只能在最开始设初值、最后取反一次。

## 📊 第六步：方法对比

| 方法 | 时间 | 额外空间 | 适用 |
|---|---|---|---|
| 逐位法 | O(8n) | 无 | 数据量小、Flash 很紧张 |
| 256 项查表 | O(n) | 1KB | 最常用（zlib 的基础版本） |
| 16 项半字节查表 | O(2n) | 64 字节 | 折中方案，小 MCU 常用 |
| 硬件 CRC 外设 | 最快 | 无 | 注意参数对齐 |
